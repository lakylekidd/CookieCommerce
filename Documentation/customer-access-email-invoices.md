# Customer access, email and invoices

Implemented and verified in Development, 15 October 2026.

## Customer access

All ten seeded mock accounts, including `admin@tiger.com`, `customer@tiger.com` and `demo01` through `demo08` at `cookiecommerce.example`, use password **123**. Development startup restores their passwords, enables the mock accounts and clears failed-login lockouts. This behavior is limited to development seeds. Public registration requires at least eight characters; production Keycloak policy retains stronger existing rules.

The back-office Customers page offers a login-access audit. Customer details show actual Keycloak status and provide **Unblock account**, **Send password reset email** and, for a customer without a login identity, **Send account invitation**. Disabled accounts remain disabled during normal administration. Ambiguous identity matches require review. Identity links preserve existing customer and order ownership IDs. Registration and password-recovery delivery are persisted and retried.

Forgotten-password responses are generic for known and unknown email addresses. Recovery requests have an IP limit, a per-address cooldown, bounded retries and expiry. Keycloak issues and validates password-change links; their lifetime is 30 minutes. Administrative endpoints require a verified admin token and account actions are audited.

## Configure outbound email

Open **Settings > Email**, enable delivery and enter the SMTP server, port, security mode, authentication credentials, sender, optional reply-to and public store URL. Save, check that authentication email synchronization reports **Synchronized**, then send a test to an address you control. Saving again retries a failed synchronization. Existing SMTP environment configuration remains a fallback until settings are saved.

Saved SMTP passwords are protected with the persistent ASP.NET Data Protection key ring. Leaving the password blank preserves it; replacement and explicit clearing are supported. Back up both the Commerce database and its key ring. The UI does not return the stored secret. Authentication email uses the same settings in Keycloak; commerce/contact messages use the shared sender and durable queue. SMTP acceptance is recorded as sent, which does not prove inbox delivery. Retries can duplicate messages after an uncertain SMTP result.

For deployment, configure private `Keycloak:AdminClientSecret` and `Communications:ServiceKey` values. AppHost rejects the development operational secret outside Development. Keep the internal template/verification key identical across the Web, Customer API and Keycloak provider. Use public HTTPS store and Keycloak URLs reachable by customers and configure the allowed sign-in return URL. Protect bootstrap administrator credentials through deployment configuration.

The Keycloak email provider is built by AppHost from `src/CookieCommerce.KeycloakEmailProvider`. It is pinned to Keycloak 26.4.7; test the provider when upgrading Keycloak. Operational account actions use a service account in the application realm. Password links are generated by Keycloak, rendered through the authenticated internal template endpoint and sent by Keycloak. A bundled default template is available when the template endpoint cannot be reached.

## Templates

**Settings > Templates** provides draft editing, sample previews, publishing, published-version history and restore-default actions. Built-ins cover password reset, account invitation, email verification, order confirmation, invoice email and PDF invoice layout. Supported placeholders are listed in the editor. Values are escaped, unsupported placeholders and executable content are rejected, and recovery templates must include their action URL.

Queued application emails retain their rendered template version. Keycloak action emails use the published template when the action link is generated. The basic PDF editor supports a heading, footer and accent color; its layout is rendered independently of email HTML.

## PDF invoices

Configure company name/address, company registration, VAT number, invoice prefix and logo in **Settings > Invoices** before issuing real invoices. Optional automatic invoice emailing runs after confirmed payment. Administrators can generate missing invoices for existing paid orders and download/email a PDF from an order's Invoice link. Customers can download invoices through their own order receipt.

Invoices retain an immutable snapshot of order amounts, billing address, company settings, template and logo. Stored PDFs remain private and require the order owner or an administrator. Number allocation is serialized, one invoice is issued per order, and retrying generation keeps the existing number and PDF. Unpaid orders are rejected. Historical real orders without a saved VAT rate require review rather than an invented rate. Set the store's actual VAT configuration before taking new orders.

Development orders have a separate `DEMO-` numbering sequence and a visible sample banner. They never consume real invoice numbers or trigger automatic invoice emails. The renderer includes embedded licensed fonts, repeated table headers, totals and page numbering.

## Verification

- AppHost build passed; Web 122, AuthenticationManagement 13 and CustomerDomain non-container tests 114 passed (249 total).
- All ten seeded identities logged in with 123. Lockout/unblock, admin authorization and anonymous/customer rejection were exercised against running services.
- Final restart retained the original data volumes, media/key directories and 100 orders. All ten original mock accounts logged in again. Login audit writes clear replayed events and lock the stream; three subsequent logins added exactly three events.
- Local SMTP capture verified a test email, a published custom Keycloak reset template, successful password change, old-password rejection and reset-link reuse rejection.
- A customer without credentials completed a first-password invitation and retained the same customer/profile ID.
- Backfill produced invoices for 100 mock paid orders. A downloaded invoice was rendered and visually inspected; manual invoice attachment delivery was exercised using local SMTP capture.

No external customer emails were sent during verification. Real SMTP credentials and company/VAT information still need configuration. Container-based CustomerDomain test suites were not included in the 249-test count. Existing dependency warnings, including Marten 8.17.0 and OpenTelemetry packages, remain and should be addressed before production deployment.
